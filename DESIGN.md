# Drover desktop experience

## Experience outcome

Drover should make one founder feel faster than the market can react. The product is one coherent machine for
changing the Product and every path to market while Claude, Codex, and specialized agents pursue exact work,
try several approaches, learn from reality, and improve the next move.

The experience is calm velocity: dark, exact, dense, responsive, and visibly alive. Aggressive capability is
expressed through immediate useful work and low coordination cost, not frantic chrome.

## One venture, two surfaces

The shipped Electron product has only two founder surfaces over one canonical venture store.

### Work

Work is the direct Claude/Codex agentic development environment. The selected provider and model are the agent
the founder talks to. Work owns:

- durable Threads grouped by founder intent and return value;
- exact Runs and isolated coding attempts;
- repository, worktree, model, cost, commands, tests, preview, and changed files;
- factual streamed activity and interruption state;
- artifacts, comparisons, evidence, decisions, and code review beside conversation;
- continuation, steering, stopping, and attempt comparison;
- provisional Product-model consequences raised by completed implementation.

Drover never inserts a persona, router, mandatory plan, or workflow vocabulary between the founder and the
selected SDK. Conversation carries direction and progress; exact material opens beside it. Do not reserve an
empty workbench before exact material exists.

Work uses native coding-client conversation geometry: a single transcript scroll owner, compact right-aligned
founder turns, unboxed agent output, and an anchored composer. Code mode exposes exact repository and model
controls. Product/GTM participation in the same Thread hides coding controls without changing the transcript,
draft, or Thread identity.

The shared composer uses `@` to include an existing venture agent by exact reference. Its final option creates a
new agent, and `/agent` plus `/add-agent` open that same founder-owned form. Saving immediately inserts the new
agent into the current draft. These commands are deterministic interface actions, never prompt text sent to a
model. In Work, an included specialist does not replace the founder's selected Claude or Codex SDK model.

### Product / GTM

Product / GTM is the founder's intent layer over the living venture model. Tools everywhere else show
state and hide what the founder is trying to do; this surface exists so the founder can see the product
laid out, say what should be different, and have that direction reach the agents exactly. It owns:

- the product map: code-proven pages laid out left to right in walk order, with page connections drawn
  only from links the code proves;
- drafted and established GTM plays;
- adopted Product truth;
- audiences, promises, offers, pricing, experience, capability, and market understanding;
- broad motions such as PLG, outbound, inbound, and partnerships;
- durable provisional Product/GTM branches;
- live work attached to the claims and relationships it may change;
- outward actions stopped at exact founder gates;
- evidence returning to the affected claims;
- contradictions, stale assumptions, unsupported claims, and missing links;
- branch comparison, conflict resolution, and selective founder merge.

It opens as a changing venture, never as a flowchart, dashboard, organization board, or pipeline builder.
Conversation is contextual and closable; the canvas owns the center. Closing conversation preserves its draft,
Thread identity, and last coherent content.

Substantive Product/GTM conversation stages one provisional local model view above the Work composer. That view
is a focused viewport into the originating `ModelBranch`, not a separate workflow artifact or parallel truth. It
begins with the founder's question, nearby current truth, supported proposals, real alternatives, evidence, and
unresolved unknowns. Relationships and causal direction appear only when the material establishes them; ordered
workflow mechanics are an earned projection for genuinely sequential work — a deliberately drafted GTM play
qualifies — never the default contract for ordinary conversation. Founder
corrections revise the same branch and view in place. Review opens the branch's exact source-bearing delta, where
the founder may selectively merge changes; the whole visual is never adopted as one opaque mechanism.

There is no Releases or System workspace. Product releases remain one outward-action kind on their causal path.

## First run

First run proves speed immediately:

1. Choose a local Product repository through the native folder picker.
2. Derive the Product name, read the repository locally, and open Work without another confirmation step.
3. Ask **What are you trying to make true?** in the ordinary Work composer, where connected Claude or Codex
   controls already live.
4. Begin safe inward Product/GTM work immediately.
5. Materialize current truth, open uncertainties, plausible motions, work, and provisional alternatives as they
   are discovered.
6. Stream useful output while grounding continues.

Do not ask for an organization, campaign, ontology, workflow, pipeline, or blank-plan approval. The success
condition is that the founder recognizes their real Product, gives a real direction, and sees useful work begin.

## Startup and return

Open the last active venture and restore its exact Work Thread or Product/GTM selection, canvas camera, rail
width, contextual-conversation state, draft, and per-Thread scroll. Legacy presentation memory may map forward,
but release selections and former mode names are discarded.

Return answers through owning Threads, canvas paths, deltas, and gates:

- what changed;
- what is still moving or queued;
- what failed, stopped, or became stale;
- what reality returned;
- what needs only founder judgment;
- which provisional Product/GTM model changed because of it.

This must not become a dashboard.

## Frame and navigation

The desktop frame has a `272px` rail, resizable to `360px`, and one remaining primary workspace. `⌘1` opens
Work, `⌘2` opens Product / GTM, and `⌘K` searches only the current surface. Below `1120px` effective width,
the rail collapses behind its launcher.

The rail remains stable beneath the venture switcher:

- Work: new Thread, search, and Pinned, Active, Needs review, Recent, and older Thread groups.
- Product / GTM: local search, available agents, and connected capabilities.

A non-root Thread menu offers **Delete chat** behind one inline confirmation. Confirmation states that live
work will stop. Deletion removes the chat from Work, revokes continuing authority rooted there, and returns to
the venture conversation; it never deletes Product truth, code receipts, or returned evidence.

Agents and capabilities are compact logo-led pills. Each names its human-readable kind and authority—Read,
Inward, or Approval—without relying on color, provider logo, or acronym. Never add a global result router,
object explorer, raw object counts, agent org chart, or market-status navigation root.

Surface changes preserve the focal subject through existing direct references. If no linked destination exists,
retain the source context and show the missing link. Do not add context stacks, generalized resolvers, or
cross-mode choreography.

## The living canvas

The default canvas holds the product map, GTM plays in both registers, current truth, several motions,
provisional alternatives, live work, outward actions, and returned evidence in one causal field. It has no fixed lanes and imposes no branch count. Large portfolios
remain legible through semantic zoom, hierarchy, compression, search, minimap, keyboard navigation, direct
selection, and return-to-context.

Current truth is solid. Provisional changes use restrained texture, explicit text, and distinct edges. They must
never visually collapse into current truth. Evidence travels on source-bearing return curves. Live work uses
short causal motion only while active. Founder gates are amber, still, and visibly stop motion.

Nodes are compact readable pills with visibly distinct Product, shared, and GTM meaning. Object names and
human-readable kinds remain visible. Selecting a node expands its description, relationships, evidence,
authority, controls, and exact review material in place; a detached side inspector must not compete with the
graph. Exact deltas, evidence, conflicts, and founder decisions may enlarge the owning node substantially.

The Product territory rests as the product map: code-proven pages as clean name-only pills in walk order,
entry pages at the left. Clicking a page expands in place what it is now — an honest, source-cited summary —
with prior founder direction and page-scoped strategy folded beneath, above a plain brain-dump input that
mints an exact Work Thread scoped to that page. Assumptions, proposals, decisions, and evidence about a page
live in its expansion, never as free-floating bubbles beside the map. Deeper machinery beneath pages stays
available through the owning page rather than becoming a backlog map.

The canvas reads left to right across one causal field: Product above, shared Product/GTM truth through the
center, and GTM below. Curved arrows preserve the causal direction. A restrained cyan-to-violet-to-rose-to-
amber-to-green spectrum marks only a relationship crossing those territories. Founder drag placement persists
as presentation and never becomes semantic truth. Agents, tools, and sources dropped on a node open exact scoped
work there; unsupported drops refuse visibly and persist nothing.

The default canvas composes itself before the founder touches it. One readable causal chapter receives the
opening frame; Product, shared truth, and GTM exert quiet positional gravity without becoming visible lanes;
related objects cluster by semantic distance; live work, provisional branches, and outward actions attach near
their exact subject; shared edge routes travel through coherent curved trunks; and expanding a node reflows only
its local neighborhood. Secondary Product features remain summarized by their owning Product object until they
carry distinct work, evidence, a model change, selection, or a focal-path consequence. New model material must
not force unrelated nodes to jump. These behaviors are automatic—do not add layout modes, settings, filters, or
required cleanup to obtain the coherent default.

A compact top-right map key keeps Product, shared Product/GTM truth, and GTM visually distinct without splitting
the model. The GTM territory is plays — workflows in two honest registers. A drafted play is an intended
workflow, sophisticated and visibly marked not yet real; an established play earned its standing by actually
running, and a draft never renders as established. Selecting a play unfolds its exact trigger, agent or tool
work, conditions, founder gates, outward actions, and return path on the existing canvas. Plays lay out at full
length, always — the length is information, never compressed into summary chapters. A running play shows derived
counts on its steps ("5 waiting on reply", "2 need your approval") with the actual people one click behind;
counts derive from real state and receipts, never founder-maintained. Product dependencies and consequences stay
connected around the play instead of becoming stages inside it. This never opens another workspace or filters
unrelated venture truth out of the model.

## Motion detail

An intended play renders as a drafted workflow in its own register; a broad route with no drafted play
remains a motion. Selecting a motion reveals only what exists: audience, problem or trigger, dependent
Product experience, Product changes it is causing, live Threads and Runs, bounded campaigns or bespoke
actions when present, pending founder actions, returned evidence, contradictions, and next useful work.

Never render empty stage frames. A motion does not need to be repeatable. A campaign does not require one
primary motion. Manual or bespoke work does not need to become a campaign.

## Product-model branch review

A branch review keeps the originating question beside:

- current Product model and proposed alternative;
- created, changed, and removed objects and relationships;
- repository work and driving motion;
- supporting, challenging, stale, and missing evidence;
- current-truth drift and exact conflicts;
- the founder decision.

The founder can continue, compare, merge all, merge selected changes, resolve conflicts, or close the branch
without deleting history. Merge is visibly founder-only. A merge does not automatically stop continuing work.

## Outward action and evidence

Any supported world crossing—release, deploy, message, publication, interview, demo, onboarding, bespoke
deliverable, partner action, or spend—uses one exact outward-action path while keeping its real name.

The review preserves context, prepared material, founder decision, execution receipt, expected return,
observation authority, evidence, and Product/GTM consequence. Nothing executes from an agent proposal or canvas
gesture. A founder interview never becomes a release; a release remains a Product release.

## Signature interaction

The defining silent demonstration is:

```text
founder direction
→ selected SDK starts exact work
→ Product/GTM alternatives materialize
→ live work attaches to what it may change
→ outward consequence stops at an amber founder gate
→ reality returns through the exact path
→ Product-model delta becomes reviewable in place
→ founder selectively merges
→ next work begins from the same context
```

It must read in under 30 seconds because it is the actual product loop, not decorative motion.

## Visual system

- Near-black neutral room: `#090B0F`, panel `#10141B`, raised `#1A202A`.
- Operating text: DM Sans. Exact machine material only: JetBrains Mono.
- Direct action and focus: `#5B8CFF`.
- Founder authority: `#E2A84A`.
- Primary text: `#D8DEE9`.
- Restrained spectrum only where a relationship crosses Product/GTM territory.
- Current truth solid; provisional truth textured; evidence source-bearing; active work briefly causal.

Avoid nested generic cards, tiny metadata, glowing AI decoration, status-dot theater, raw prose walls, and
empty decorative canvas. Every primary screen has one clear center and one clear next action.

## Complete state design

Design and verify first run, empty venture, model loading, partial grounding, active and queued work, several
approaches, budget pause, missing auth, failed/interrupted/restarted Run, stale branch, merge conflict, founder
gate, outward failure, evidence return, silence, offline, dense canvas, `1440×900`, `1280×800`, 200% zoom,
and reduced motion.

Transport errors are translated into founder recovery. `/api/... failed (502)` is never primary UI.

## Accessibility and motion

Every interactive element is keyboard reachable and has a visible focus state. Meaning never depends on color,
motion, logo, or acronym alone. At 200% zoom, primary actions and exact decisions remain visible without two-axis
page scrolling. Reduced motion removes travel and pulsing while retaining state distinctions and causal order.

## Forbidden experience

Do not restore founder-facing System, Architecture, Firm, Bet, Fork, Teammate, Heat, organization, crew, or
holding-company language. Use pipeline only for a literal throughput pipeline. Do not restore fixed pipeline
lanes, a Releases workspace, release navigation state, blank campaign/release forms, duplicate canvases, the old
Atlas/Now/Workyard shells, or compatibility UI. Historical adapters may remain read-only until migration is
proven; they never dictate current product language or interaction.
