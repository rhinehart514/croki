# Living Product Picture — build spec

## What this feature is, in one breath

GTM IDE scans a product's code and reports only cited facts. That truth is honest but
shapeless: it has no notion of the product's *things*, how they relate, what users are
trying to do, or what state they're in. The **Living Product Picture** is the editable,
interpretive model of the product that sits on top of that truth — its core objects,
their relationships, the user goals, the key states — generated by rented intelligence,
edited by the founder, accumulated as an append-only history, and pinned with real-world
feedback so it stays current instead of going stale. Downstream subsystems (every agent
the IDE runs) re-ground from this picture instead of from the thin 4-line product blurb
they read today.

The picture is **interpretation**, not truth. That single distinction drives every design
choice below.

---

## The hard line this feature must not cross

The product object model is an *interpretation* of the code, not a *fact* about it.
Three AGENTS.md invariants draw the line this feature must not cross:

- **"Grounding does not shape"** (AGENTS.md:192-201): the scan and
  `product-understanding.mjs` report only cited, reproducible reality and never impose a
  conceptual shape. A taxonomy of "objects and relationships" is exactly the kind of shape
  that invariant forbids in the truth layer.
- **The citation rule** (AGENTS.md:152-153): "the citation rule binds the truth layer …
  the scan, `product-understanding.mjs`, **engine/measure derivation** — are proven by
  production-code citations or marked inferred or blind." This is the most load-bearing
  line for the engine change in this spec: it puts engine/measure derivation *inside* the
  truth layer. Anything that moves an engine health number must be backed by cited reality,
  not by founder-editable interpretation.
- **"Never seeded"** (AGENTS.md:160): engine and node health are "derived from real state
  (scan, run ledger, connectors, decisions), never seeded." A subsystem with no real signal
  must say so honestly.

The `ProductModel` is none of those real-state sources. By this spec's own design it holds
`speculative` founder/model guesses (the `provenance` field on Thing, Relationship,
UserGoal, ProductState) and is mutated by the founder through `ReviseProductModel`. So it is
interpretation, and it must never become an input to any engine/measure health or confidence
derivation. The engine reads only the truth-grade sources the citation rule names; the
product model rides alongside as a separately-labeled interpretation, never folded in.

Therefore:

- **Nothing in this feature is added to `scan.mjs` or `product-understanding.mjs`.** Those
  two files stay pure (the read crew confirmed this is guarded by `scan.test.mjs`, required
  per AGENTS.md Verification). The product picture reads their output as read-only grounding;
  it never writes back into them.
- The picture is generated by an **injectable generator** with an honest blank default that
  refuses rather than fabricates, plus a live `createClaude*` variant — exactly the pattern
  of `ideation.mjs` (`createClaudeIdeator`, ideation.mjs:61) and `composition.mjs`. This
  respects AGENTS.md:173 ("the host owns truth, state, and the gate; the intelligence is
  rented") and AGENTS.md:195-196 (deciding interpretive shape is "ideation's job, rented from
  the model").
- The founder edits the picture. The host owns the durable state and the edit machinery;
  the model only proposes the first draft and, on request, re-derives. This is the same
  truth/state/gate split the whole product runs on.

## The aggregate: `ProductModel`

A new domain aggregate, persisted the same way `OutcomeProgram` is. One `ProductModel` per
project (keyed by `projectId`), versioned along a lineage so edits accumulate.

### Shape

```
ProductModel {
  id                 // "product-model-<slug>" ; stable across revisions (lineage continuity)
  lineageId          // === id at birth; preserved across revisions
  previousModelId    // prior version's id, or null
  version            // 1, bumped on each revision
  projectId
  generatedBy        // "claude" | "blank" | "founder" — provenance of the current draft
  groundingRef       // { evidenceState, citationCount, scannedAt } — a SNAPSHOT of the truth
                     //   the picture was derived from, so a stale picture is detectable.
                     //   NOT the truth itself; a pointer to which scan it interpreted.

  things[]           // the core product objects (nouns)
    Thing {
      id             // "thing-<slug>"
      name           // e.g. "Project", "Win event", "Operator"
      kind           // free-text interpretive label (entity / actor / artifact / event …)
      summary        // one plain-English line
      evidence[]     // Citation[] — { label, file, line, text }; may be empty (interpretive)
      provenance     // "derived" (cites real file:line) | "speculative" (founder/model guess)
    }

  relationships[]    // how the things relate
    Relationship {
      id             // "rel-<slug>"
      from           // Thing.id
      to             // Thing.id
      label          // e.g. "creates", "belongs to", "triggers"
      summary
      provenance     // "derived" | "speculative"
    }

  userGoals[]        // what users are trying to accomplish (the outcomes the product serves)
    UserGoal {
      id             // "goal-<slug>"
      actor          // who wants it (a Thing.id of kind actor, or free text)
      goal           // plain-English statement
      relatedThings  // Thing.id[]
      provenance
    }

  states[]           // key states a core object moves through (lifecycle the product expresses)
    ProductState {
      id             // "state-<slug>"
      thingId        // Thing.id this state belongs to
      name           // e.g. "draft", "published", "attributed"
      summary
      provenance
    }

  pinnedSignals[]    // the "living" layer — real-world feedback pinned onto a specific element
    PinnedSignal {
      id
      signalId       // the FeedbackSignal.id from feedback-ledger.mjs (the source of truth)
      target         // { kind: "thing"|"relationship"|"goal"|"state"|"model", id }
      type           // mirrors the FeedbackSignal type (ObservedOutcome, FounderEdit, …)
      summary
      observedAt
    }

  createdAt
  updatedAt
}
```

**Why `provenance` per element, not per model.** This mirrors the truth layer's
one-directional valve. `opportunity-engine.mjs:72-73` demotes any `origin:"derived"`
proposal that carries zero evidence citations down to `"speculative"`. The product model
applies the same valve element-by-element: a `Thing`/`Relationship`/etc. claiming
`provenance:"derived"` with an empty `evidence[]` is demoted to `"speculative"` by the host
at command time (see "the pollution guard" below). An interpretive guess can never launder
itself back as cited fact. This is the AGENTS.md:152-159 citation rule applied at the
interpretive boundary, not in the truth layer.

**Why `groundingRef` is a snapshot, not the live truth.** The picture interprets a specific
scan. If the code is re-scanned and the evidence changes, the founder needs to know the
picture is now interpreting stale truth. `groundingRef` records what it was derived from
without copying the truth into the aggregate (respects "grounding does not shape" — truth
is referenced, never absorbed and re-shaped).

## Commands → events → projection (reusing the existing machinery)

The DDD.md invariant (DDD.md:125-127) is that **the domain event log is authoritative**:
every state-changing command records an append-only event carrying the full aggregate, and
`program-projection.mjs` folds events back into current state, proven equal to the stores by
`program-projection.test.mjs`. The product model reuses this exact machinery. Three commands,
three event types, three projection cases.

### `DeriveProductModel`

The first-draft generation. Runs the injectable generator over the scan grounding, builds a
full `ProductModel` aggregate, appends one event, returns the projected record.

- **Generator call** — `generate({ grounding, repo, market })` (the injectable, below).
- **Pollution guard** — before persisting, the host runs `normalizeProductModel` (mirrors
  `normalizeProposal`, opportunity-engine.mjs:65): it owns ids/timestamps/provenance, and
  demotes any element marked `derived` with zero citations to `speculative`.
- **Event** — `type: "ProductModelDerived"`, `aggregateType: "ProductModel"`,
  `aggregateId: model.id`, `data: <FULL model>`. The full-aggregate-in-`data` rule is
  load-bearing (DDD.md:125, program-projection.mjs:142-146): a stub breaks rebuild.
- **Return** — `syncProductModelStoreFromEvents(projectId).find(m => m.id === model.id)`.

Pattern source: `CreateOutcomeProgram` (domain-commands.mjs:66-75).

### `ReviseProductModel`

A founder edit (or a model re-derivation the founder accepted). Loads the current model,
applies the changed bags, bumps `version`, sets `previousModelId = current.id`, preserves
`lineageId`. This is how edits **accumulate and compound** — every edit is a new version on
the lineage, the old version stays in the event log, nothing is overwritten in history.

- Mirrors `reviseOutcomeProgram` (program-store.mjs:254-280) and the `DefineMeasurementPlan`
  revision command (domain-commands.mjs:77-88).
- **Whitelist the editable bags**: `things`, `relationships`, `userGoals`, `states`,
  `generatedBy`. `pinnedSignals` is NOT founder-editable here — signals arrive only through
  `RecordProductSignal` (the founder edits the *model*, the world edits the *signals*).
- Re-run `normalizeProductModel` so an edited element that claims `derived` without evidence
  is demoted, exactly as on derive.
- **Event** — `type: "ProductModelRevised"`, `data: <FULL revised model>` (full aggregate,
  not a diff — the rebuild reconstructs the record, not a patch).

**"Ripple the change."** Because every downstream model call re-grounds from the projected
current model (via the context provider, below), a revision automatically ripples: the next
agent run, the next assemble-context call, and the engine's Context health all read the new
version. No separate propagation step — the projection *is* the ripple. This is why the
picture must be the single source the provider reads, not a copy.

### `RecordProductSignal`

The "living" stroke: a real-world `FeedbackSignal` gets pinned onto a specific element. This
closes the gap the reality-feedback read crew found — today a signal carries a `nodeId` but
nothing joins it back onto the product model.

- Input: a `FeedbackSignal` (already persisted in `feedback-ledger.mjs` — that ledger stays
  the source of truth for the signal itself) plus a `target` (`{kind, id}`) naming which
  Thing/Relationship/Goal/State it pins to (or `model` for a whole-picture signal).
- The command appends a `ProductSignalRecorded` event carrying the `PinnedSignal` record. The
  projection folds it into `model.pinnedSignals`. The signal's body is NOT copied — only its
  `signalId`, target, type, summary, and timestamp — so `feedback-ledger.mjs` remains the
  authoritative store of the signal and the picture holds only the pin.
- **This does not duplicate the existing feedback path.** The existing path
  (`recordFeedbackSignalsFromRun`, feedback-ledger.mjs:136) fans feedback out to revise
  `AgentCreationPolicy` and stays untouched. `RecordProductSignal` is an *additional*
  consumer that pins the same signal onto the picture. Feedback can do both: revise the
  policy (compounding rule) AND light up the picture (living model). Surfacing both rather
  than blending them respects ENGINEERING.md "surface conflicts, never blend."

### Projection fold — the load-bearing integration point

Add three cases to `applyDomainEvent` (program-projection.mjs:59) and a new collection. The
read crew's warning is exact: the `default` branch (program-projection.mjs:150-153) silently
no-ops unknown event types, so a missing case appends and persists but never projects,
silently breaking the reconciliation guarantee.

- `emptyState()` (program-projection.mjs:48-56) gains `productModels: new Map()`.
- `ProductModelDerived` → `state.productModels.set(data.id, { ...data })`.
- `ProductModelRevised` → `state.productModels.set(data.id, { ...data })` (the revised
  record keeps the same `id` for continuity per the lineage convention, mirroring how
  `reviseOutcomeProgram` keeps the record id — so a revision overwrites the single current
  record while the *event log* retains every version. This matches the program aggregate,
  which is also one-record-per-lineage in the projection, versioned in the log).
- `ProductSignalRecorded` → fetch `state.productModels.get(event.aggregateId)`, push the
  `PinnedSignal` onto its `pinnedSignals` (mirror `MeasurementPlanDefined`'s fold-onto-
  parent at program-projection.mjs:68-73).
- `rebuildProjectState` (program-projection.mjs:165-175) returns
  `productModels: [...state.productModels.values()]`.

### Store

New `brain/src/product-model-store.mjs`, modeled on `program-store.mjs`:

- `buildProductModel(input, options)` — pure builder; stamps `id`, `lineageId`/
  `previousModelId`/`version`, `projectId`, `createdAt`/`updatedAt`, the domain bags
  (mirrors `buildOutcomeProgram`, program-store.mjs:140-176).
- `normalizeProductModel(model)` — the pollution guard; whitelists fields and demotes
  `derived`-without-evidence elements to `speculative` (mirrors `normalizeProposal`).
- `loadProductModelStore` / `saveProductModelStore` — atomic temp-file write + rename
  (program-store.mjs:60-65, 108-116); file at `~/.gtm-ide/product-models/<projectId>.json`.
- `syncProductModelStoreFromEvents(projectId, options)` — diffs snapshot ids against
  projected ids and overwrites with the projection (mirrors
  `syncProgramStoreFromEvents`, program-store.mjs:118-128).
- `getProductModel(projectId, options)` / `reviseProductModel(...)`.

**No legacy migration machinery.** `program-store.mjs` carries `migrateProgram` /
`LEGACY_STATUS_MAP` only because its schema changed v1→v2. A fresh aggregate starts at
`schemaVersion: 1` clean and adds a migration fold only if its on-disk shape later changes.

## The injectable generator (rented intelligence)

New `brain/src/product-model-generator.mjs`, modeled exactly on `ideation.mjs`.

- **Contract** — `generate({ grounding, repo, market }) -> { ok, model, meta }`, where
  `model` is the bags `{ things, relationships, userGoals, states }` (the command stamps ids/
  versions/provenance; the generator proposes content).
- **Blank default** — `blankGenerate` returns `{ ok: true, model: { things: [], … }, meta: { blank: true } }`
  and never fabricates. Refusing-rather-than-faking is the same honest-blank discipline as
  `blankIdeate` (opportunity-engine.mjs:54-56) and the context providers' `null` return.
  This satisfies the rule that the host without rented intelligence reports the gap, not a
  fake picture.
- **Live variant** — `createClaudeProductModeler({ cwd, model, maxTurns })` runs a subagent
  on the founder's subscription via `createClaudeAgentInvoker` (agent-bridge.mjs), passing
  `{ grounding, market }` as read-only context. Mirrors `createClaudeIdeator`
  (ideation.mjs:61-73). OAuth-first, no key, no send path.
- **Doctrine in markdown, not host code** — the modeling instruction lives in an editable
  `~/.claude/agents/gtm-model-product.md` plus an exported `PRODUCT_MODEL_PROMPT` string,
  exactly as `IDEATION_PROMPT` + `gtm-ideate-channels.md` do (ideation.mjs:22-56). The prompt
  tells the model: derive things/relationships/goals/states FROM the grounding and a few key
  repo files; cite `file:line` for anything marked `derived`; mark genuine guesses
  `speculative`; never invent a file or a citation.

Injection point: `DeriveProductModel` takes `{ generate = blankGenerate }` in its options,
exactly as `generateOpportunities` takes `{ ideate = blankIdeate }` (opportunity-engine.mjs:101).
Tests inject a fake; the server/operator inject `createClaudeProductModeler`.

## Context provider (downstream re-grounding)

New `createProductModelProvider(model)` in `brain/src/context/providers.mjs`, exported from
`brain/src/context/index.mjs`, registered in `providersFromContext`.

- **Shape** — closure over the editable model; `name: "product-model"`, `layer: "base"`;
  `contribute()` returns `null` (honest blank) when the model has no things, else a compact
  text block: the things, the key relationships, the user goals, the states, and any pinned
  real-world signals (the living layer the model otherwise never sees). Mirrors
  `createProductProvider` (providers.mjs:20-52) including the `null`-on-empty contract
  (providers.mjs:24).
- **Exact provider-text framing (so the block can never read as truth at the consumption
  point).** `createProductProvider` already emits a cited-truth `product` block at the same
  `layer: "base"`, so a reading agent sees both blocks in one assembled prompt. The
  interpretation block must be visibly, unmistakably *not* cited reality:
  - The block must open with this exact header line, verbatim:
    `INTERPRETATION (founder-editable, not cited reality):`
  - Every element renders its provenance inline, mirroring how `createProductProvider`
    spells out `attribution BLIND` / `proven from product code` (providers.mjs:32-39). A
    `derived` Thing renders with its `file:line` citation, e.g.
    `- Thing: Project [derived: brain/src/scan.mjs:204]`. A `speculative` Thing renders with
    an explicit unproven marker and NO citation, e.g.
    `- Thing: Operator [speculative — founder/model guess, not proven from code]`. A
    speculative element is never emitted as a bare fact.
  - This guarantees the two `base`-layer blocks are distinguishable in the prompt: a cited
    Win event from the `product` block reads as proven; a `speculative` Thing reads as a
    labelled guess. An interpretation block that read like truth would itself be
    truth-pollution at the consumption point even if the aggregate is clean — the header and
    the inline markers prevent that.
- **Registration** — one guarded push in `providersFromContext` (providers.mjs:150-158):
  `if (context.productModel) providers.push(createProductModelProvider(context.productModel));`.
  Because both live consumers (`agent-bridge.mjs:118` and `server.mjs:746`) route through
  this single adapter, this one line lights up the editable model in every downstream agent
  prompt — this is the mechanism by which a founder edit *ripples* into what every agent
  reads.
- **The conflict to resolve explicitly (ENGINEERING.md "surface conflicts, never blend").**
  The existing `createProductProvider` emits the *truth* (cited scan facts). The new provider
  emits the *interpretation*. They are different layers and both should run: the scan
  provider stays the cited-fact map, the product-model provider adds the interpretive shape
  the truth deliberately lacks. They do not conflict because they answer different questions
  (what is provably there vs. how it's organized for the user). Keep both registered; do not
  have one replace the other. The exact provider-text framing above (the verbatim
  `INTERPRETATION (founder-editable, not cited reality):` header plus inline per-element
  provenance markers) is what makes a reading agent never mistake a `speculative` thing for a
  cited fact.
- **Recognized-key hygiene** — add `productModel` to the destructure at `agent-bridge.mjs:121`
  so it is consumed as an assembled layer and not double-emitted as raw `...rest` JSON.

## Engine: the Context subsystem derives from real scan state

Today `deriveContext` (engine.mjs:159-176) returns a hardcoded `health: 88, confidence: 85`
whenever any context connector is ready, regardless of what the scan proved. That is the
seeded value AGENTS.md:160 forbids ("derived from real state … never seeded"). This feature
makes Context health reflect the **real scan/grounding state** — and nothing else.

**The invariants this change must answer to.** Engine derivation lives *inside* the truth
layer. The citation rule (AGENTS.md:152-153) binds "the scan, `product-understanding.mjs`,
engine/measure derivation" to cited reality. The never-seeded rule (AGENTS.md:160) requires
health be "derived from real state (scan, run ledger, connectors, decisions)." So the only
admissible inputs to `deriveContext` are exactly those real-state sources. The
`ProductModel` is NOT one of them — it is founder-editable interpretation holding
`speculative` guesses — so it is **never an input to this derive**. (How "how grounded is the
interpretation" gets surfaced, if wanted, is handled separately below; it never lands in the
Context health number.)

**Resolved shape ambiguity (verified at the call site).** `getEngineState` is called with the
**raw scan report**, not the understanding object (`server.mjs:711` passes
`getWorkspace(...).report`). The raw report has NO `productName` field — confirmed against
`scan.mjs:333-371`, whose top-level keys are `repo`, `scannedAt`, `filesScanned`, `stack`,
`headline`, `analytics`, `attribution`, `winEvent`, `funnel`, `gaps`. `productName` exists
only on `buildProductUnderstanding` (`product-understanding.mjs:34`). So `deriveContext` must
read only fields that actually exist on the raw report: `report.repo`,
`report.filesScanned`, `report.stack` (array), `report.winEvent.found`, and the per-section
citation arrays `report.winEvent.citations`, `report.analytics.citations`,
`report.attribution.citations`. It must NOT read `report.productName` (always `undefined`
on the raw report — keying on it would send every grounded scan into the "read nothing"
branch, which is itself a constant/seeded failure mode). The flattened `evidence[]` /
`evidenceState` / `blindSpots[]` live on the *understanding*, not the raw report — do not read
them off `report` either.

Replace the binary "report exists → 88" with a graded derive mirroring `deriveMeasure`'s
structure (engine.mjs:221-292), keyed on fields that exist on the raw report:

1. No `report` → keep the honest "open a workspace" blank (engine.mjs:162-165, unchanged).
2. Report present but `report.filesScanned === 0` (or `!report.repo`) → grounding ran but
   read nothing; low health, issue naming the empty scan.
3. Scan read files but is **ungrounded** — total citation count is zero
   (`report.winEvent.citations.length + report.analytics.citations.length +
   report.attribution.citations.length === 0`) AND/OR `report.stack.length === 0` → context
   exists but nothing is cited; mid health, action "scan a repo with real product code." This
   is the exact case that wrongly shows 88 today (a ready context connector with a real but
   uncited report).
4. `report.winEvent.found === false` (proven hole) → grounded but blind on the win event; cap
   health in the ~40-60 band and surface the blind spot, exactly as Measure does for blind
   attribution (engine.mjs:251-258).
5. Citations present (any of the per-section arrays non-empty), `report.stack.length > 0`,
   `report.winEvent.found === true`, and context connectors ready → the real high band
   (88/85), now *earned*.
6. Fold the scan `gaps` into `activeIssues` so the Problems rail
   (`deriveTopRecommendations`/`deriveInvestigations`) can route to Context when the scan is
   thin — impossible today because Context never drops below 70.

Keep the connector-readiness check (engine.mjs:168) as one input, but it is no longer the
sole gate to the high band. The signature stays `deriveContext(connectors, report)` — it does
NOT also take the product model. Adding the product model to this signature would be the
literal seam that lets interpretation flow into truth-layer derivation, so it is excluded by
construction.

**Struck: feeding the product model into Context health.** An earlier draft proposed an
"optional second pass" where `deriveContext` would also read the `ProductModel`'s
`pinnedSignals` and its `derived`-vs-`speculative` element counts to enrich Context health.
That is removed, and it must not be re-added. It would wire founder-editable interpretation —
which by design holds `speculative` guesses and is mutated by `ReviseProductModel` — into a
truth-layer health number. A founder editing the interpretation, or the model proposing a
speculative Thing, could then move a number AGENTS.md:152-153 and AGENTS.md:160 require to
reflect only proven reality. That is exactly the truth-pollution this feature exists to
refuse. There is no `deriveContext` signature change accepting the product model, and no such
read at the engine call site.

**Where observed feedback legitimately moves a number.** If real-world feedback should affect
Context health, it must travel through an already-truth-grade source, not through the editable
aggregate: the `FeedbackSignal` records in `feedback-ledger.mjs` (`normalizeRunFeedback`
emits `ObservedOutcome`/`FounderEdit`/`RunFailure` records) and the run ledger — both of which
AGENTS.md:160 names as "real state." Pinning a signal onto the picture
(`RecordProductSignal`) is a separate, additive consumer; it never becomes the engine's
input.

**If "how grounded is the interpretation" is genuinely wanted**, surface it as its own,
explicitly-labeled **interpretation-quality indicator on the Product overlay** — e.g. "12 of
18 elements cited; 6 speculative" computed from the `ProductModel` and shown on the overlay
UI. It is a property of the interpretation, displayed where the interpretation lives. It is
NEVER folded into the Context subsystem's `health`/`confidence`, and it is never read by
`engine.mjs`. Keep interpretation-grounding and product-truth in separate outputs with no
shared value.

## Server + MCP exposure (both front doors, in lockstep)

The three commands funnel through the single chokepoint `executeDomainCommand`
(domain-commands.mjs:25). Lockstep is a hand-maintained convention — there is no parity test
— so each door gets the same shape.

1. **Core** (domain-commands.mjs): three `case` arms + three exported functions shaped like
   `CreateOutcomeProgram` (domain-commands.mjs:66). The live generator is injected here for
   `DeriveProductModel`.
2. **Projection** (program-projection.mjs:59): the three event cases above. **Without these,
   replay loses the model** (the silent `default` no-op).
3. **Door 1 — Human HTTP** (`server.mjs`): three `if`-routes, each reading body, calling
   `loadProject()`, then `executeDomainCommand("DeriveProductModel", {...body, projectId}, {projectId})`,
   returning JSON; template is `POST /api/program-workflows` (server.mjs:500-519).
   Suggested routes: `POST /api/product-model/derive`, `/revise`, `/signal`. `DeriveProductModel`'s
   route injects `createClaudeProductModeler` as the generator. Also: the assemble-context
   route (server.mjs:746) sources the current `ProductModel` (via `getProductModel`) and passes
   it as `productModel` so the `product-model` provider lights up in downstream prompts. The
   engine route (server.mjs:711) does **NOT** pass the product model — Context health derives
   from the raw scan report and connectors only (see the Engine section). Wiring the product
   model into the engine call is the seam the truth-pollution refutation forbids; keep it out.
4. **Door 2 — Brain MCP** (`mcp.mjs`): three `brainPost` wrappers + three `TOOLS` entries
   (template mcp.mjs:209 + the registration array). This door is an HTTP client to Door 1, so
   the Door-1 routes must exist first. Keep tool count 10-30, names unique, descriptions
   >40 chars with an object schema (`mcp.test.mjs` floor).
5. **Door 3 — Operator MCP** (`operator-runtime.mjs`): three `TOOLS` entries (note
   `input_schema`, snake_case) + three `executeTool` arms calling `executeDomainCommand`
   in-process (template `create_program`, operator-runtime.mjs:988-1003). `operator-mcp.mjs`
   reflects them automatically. The verbs `Derive`/`Revise`/`Record` are safe — they do not
   match the forbidden-verb regex `/approve|send|publish|deploy|charge/i`
   (`operator-mcp.test.mjs`), so the picture stays inside the wall (AGENTS.md:163-169, nothing
   sends/publishes/charges).
