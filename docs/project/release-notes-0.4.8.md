# Croki 0.4.8 application awareness plan

Croki 0.4.8 lets a fresh native model understand the application it is changing
without adding a Croki product-thinking harness or asking the founder to restate
the product on every Thread.

## Foundation

- `application_observe` composes the current `.croki/application.json` revision,
  the invoking Thread's branch, worktree, latest checkpoint and changed files,
  project-wide checked screens, and bounded Croki Senses evidence.
- Declared direction is reported as project-declared with approval unverified.
  Repository activity and model observations never become application truth.
- Checked screens retain their originating Thread and turn, current source
  worktree attribution, immutable checkpoint when available, and attachment
  frame. A missing code revision is explicit. A qualified
  source-Thread-plus-screen reference remains unambiguous when a Thread is
  forked.
- A provider can request an explicit baseline and target. Croki returns factual
  route, size, interaction, console, network, and action-count deltas; the native
  model decides what those facts mean for users and the product mission.
- `application_screen` reopens the exact preserved PNG only when its qualified
  reference belongs to the invoking Thread's project.
- Output is bounded, source-filterable, freshness-aware, and honest about stale,
  unavailable, incomplete, or truncated evidence.

## Product boundary

There is no Product mode, PM persona, mission score, knowledge dashboard,
background synthesis loop, or mandatory response template. Application
awareness is evidence supplied to the selected provider's native reasoning.

The composer continues to show declared released and building direction, now
with the approval boundary stated explicitly. Checked evidence remains in
Preview and Review rather than creating another founder workflow.

## Provider boundary

Providers connected to Croki MCP can observe and reopen the full frame. OpenClaw
through ACP and external OpenCode sessions currently receive injected bounded
lineage but not Croki MCP tools; 0.4.8 must describe that limitation rather than
claiming identical evidence access for every provider.

## Release proof

- contract tests reject unbounded reads and preserve the declared/observed split;
- MCP tests verify read-only annotations, qualified screen lookup, exact image
  output, and rejection of a guessed cross-project reference;
- UI-history tests preserve Thread-owned images and projection provenance;
- provider evaluations compare native answers with and without awareness for
  user understanding, responsibility transfer, mission continuity, unsupported
  assumptions, and source correctness.

The release is successful only if blinded provider evaluations improve product
judgment, not merely the amount or polish of generated prose.
