# Croki 0.4.7 — Application Sense

Croki 0.4.7 makes the repository aware of the product it belongs to.

You keep building through ordinary files, Git, Threads, worktrees, terminals,
Preview, Review, and PRs. Croki now gives those surfaces a shared understanding of
what the application is, what is true today, what is being built, and where the
current exploration belongs. No product brief needs to be pasted into every Thread.

## A visual product world

Opening a `.croki` object no longer feels like opening configuration. Croki generates
the visual world appropriate to its boundary:

- **Application** connects released reality, building intent, active Concepts, the
  current Release, product consequences, market expression, proof, and provenance.
- **Concept** enters an isolated exploration while preserving its visible path to the
  parent, inherited facts, challenges, Product and GTM hypotheses, relationships, and
  evidence.
- **Release** tells the shipping story: what people experienced before, what changes
  after, what disappears, how the change will be demonstrated, and how we will know it
  worked.
- **Venture** shows shared thesis, audience, distribution, capabilities, constraints,
  and opportunities across independently coherent applications.

The source remains available through **Inspect .croki source**. Croki does not add a
custom language, an index file, or a manually maintained graph.

## Fresh perception for every agent

Before each provider turn, Croki reads a fresh bounded snapshot from the canonical
project root. Application, active Release, parent Venture, current Concept, relevant
project activity, and checked-screen evidence remain separately sourced and clearly
labelled as data—not instructions.

Invalid, missing, unsafe, unsupported, unreadable, or oversized `.croki` objects fail
open. Native coding continues. `.croki` cannot run commands, import prompts, grant
authority, install dependencies, contact services, or silently redefine product truth.

## Explore separately

**Explore separately** creates one self-describing Concept and opens a scoped worktree
Thread on `croki/concept/<id>`. The Concept inherits relevant parent reality without
changing it. There is no `concepts/index.json`; Croki discovers individual objects.

Concept integration remains an explicit review boundary. Code can merge independently
from a proposed update to durable application reality. Archived explorations preserve
their hypothesis and evidence but leave ordinary perception.

## Checked-screen memory

0.4.7 also lets models return to interfaces they actually inspected:

- Successful `preview_snapshot` calls preserve the PNG, route, dimensions,
  diagnostics, action count, source turn, and observation time.
- The read-only `ui_history` sense lists or reopens an exact prior checked screen.
- Preview shows recent checked screens without replacing the live page.
- A visible implementation turn ends with one honest **Checked _n_ screens**, **Not
  checked**, or **Check unavailable** receipt. Backend-only turns remain unchanged.

Checked means Croki preserved a screen the model inspected. It is evidence, not an
automatic design verdict or claim of complete state, accessibility, breakpoint, or
production coverage.

## The boundary

The foundational ontology is deliberately small:

```text
Venture
└── Application
    ├── Release
    └── Concept
        └── Concept
```

Evidence, relationships, Product and GTM lenses, decisions, Threads, worktrees,
screenshots, plans, and prompts support those worlds. They do not become more `.croki`
kinds. A new kind earns a boundary only when an agent can enter it, inherit context,
work independently, and later reconcile it with a parent.

Croki 0.4.7 is the foundation for building many ideas independently while keeping the
result one product.
