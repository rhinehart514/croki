# End-to-end experience architecture for Drover

**Status:** exploration evidence only. The authority files adopt selected corrections and explicitly defer
the semantic-zoom capacity layer, reusable-method promotion, and global cross-mode search until a real
release-and-evidence loop runs.

## Experience thesis

Drover is one continuous venture-development experience expressed through three coherent lenses:

```text
Work  →  Product / GTM  →  Releases
  ↑                            ↓
  └────── returned evidence ───┘
```

The arrows describe causal movement, not required navigation stages. A founder can enter anywhere.

> I decide what should become true, Drover helps build it, I see how it changes the venture, I release it
> into the world, and evidence returns to shape the next work.

Conversation remains critical, but it does not need to be the permanent visual center of Product / GTM or
Releases. The release—not the Thread or agent—is the unit of market movement.

## Mental model

The founder works with:

- the **venture**: repository, Product, go-to-market, work, releases, and evidence;
- **Work**: durable Threads where the founder and agents change the venture;
- **Product / GTM**: the visible model of how value reaches the market and what returns;
- a **release**: concrete Product value moving into the world with an evidence path.

Agents, Runs, worktrees, diffs, checkpoints, tools, and provider sessions are implementation depth. They
appear when useful but are not top-level product concepts.

```text
Venture
├── Work changes it
├── Product / GTM makes it legible
└── Releases move it into reality
```

## Persistent frame

The desktop frame keeps venture identity, the three founder modes, a mode-owned rail body, and one dominant
active surface.

```text
┌──────────────────┬─────────────────────────────────────────────────┐
│ Drover           │                                                 │
│ Work             │                                                 │
│ Product / GTM    │              Active surface                     │
│ Releases         │                                                 │
│                  │                                                 │
│ Mode context     │                                                 │
│                  │                                                 │
│ Settings         │                                                 │
└──────────────────┴─────────────────────────────────────────────────┘
```

The rail is approximately 220–240px. Only the selected mode's relevant content appears beneath the mode
switch. Do not simultaneously display Threads, Product/GTM scopes, releases, agents, workflows, and evidence.

Changing mode changes representation, not canonical identity. The carried focus is the founder's focal
subject. Existing direct references open the nearest exact linked representation; when none exists, the
destination shows the missing link and retains the source context.

## Beginning-to-end journey

### Enter the venture

On first use, the founder connects a repository. Drover inspects repository structure, branch and git state,
package scripts, public Product language, recent changes, configured providers, and existing venture data.
It returns a provisional interpretation rather than an empty setup flow. The founder corrects it in ordinary
language. Drover does not require a taxonomy, blank canvas, workflow configuration, agent assignment, or
release form before first value.

Returning use restores active work. Otherwise it shows no more than three truthful returns: work ready for
review, work still moving, a release blocked on founder judgment, or evidence that challenged understanding.

### Start or continue Work

Work is the coding and execution surface. Its rail shows New Thread, mode-local search, and Threads grouped
by their return value. A Thread row communicates intent, meaningful state, relevant participant, returned
result or failure, and recency. There is no separate Agents section.

A local Thread draft becomes durable on first send. Work may begin from the whole venture, exact code or a
diff, a Product capability, an audience or offer, a release, returned evidence, or a visible gap. The selected
context attaches through exact references.

The founder sends direction and regains control immediately. Conversation contains visible interpretation,
meaningful progress, contradictions, results, verification, failure, and founder questions. Raw SDK events,
tool calls, and low-value narration remain collapsed.

When exact material exists, Work becomes conversation beside material. The material surface can display code,
diffs, previews, verification, terminal output, comparisons, exact artifacts, and founder gates. Steering,
critique, parallel attempts, stop, and recovery remain in the same Thread.

### Review exact work

Agent completion is not Product completion. Review shows exact changed files and diff, checks, preview,
unresolved failures, lineage, and the exact founder-held consequence. Apply, commit, push, pull request,
deploy, publish, and send remain separate consequences. Nothing is inferred from a completed model turn.

### Translate work into venture meaning

A verified Product change raises a reviewable Product consequence and distribution question. The proposed
interpretation is editable, rejectable, and visibly provisional until adopted. Repository support stays one
gesture away. Work that does not change Product surfaces only the GTM, evidence, or operational consequence
its truth supports.

## Product / GTM canvas

Product / GTM is a full spatial workspace. Conversation opens only when the founder asks Drover or needs to
inspect and direct a selected object or path.

```text
Product value → market movement → returned evidence
                         ↖ changed understanding
```

An explored canvas grammar placed durable Product and distribution capacity above active paths and unfolded
selected execution detail below. This remains a hypothesis until the real loop proves what deserves spatial
permanence.

At rest, the canvas should make durable capabilities, customer value, audiences, offers, distribution,
active release paths, evidence, and material gaps legible without exposing every Run, provider session,
tool call, artifact, or old release.

The intended reading questions are:

1. What value exists?
2. Who is it for?
3. How does it move?
4. What is active?
5. What returned?
6. What is disconnected?
7. What deserves work next?

Nodes are editorial rather than dashboard cards: a name, quiet type, concise statement, and optional current
state. Agent presence is temporary and attached to the exact object being changed. After completion the
agent presence disappears while the artifact, verification, and contribution remain.

The most important Product / GTM objects may be gaps:

- capability has no distribution path;
- claim lacks Product support;
- audience has no credible offer;
- release has no measurement or evidence path;
- returned evidence changed no understanding.

A gap is selectable and can begin exact Product, research, positioning, coding, or distribution Work.

The proposal also explored promoting repeated verified methods into reusable capacity. Authority deliberately
defers that mechanism and vocabulary until repeated real use proves a founder need.

## Product / GTM to Releases

Preparing a release carries forward exact Product delta, customer consequence, audience, supported claims,
available distribution mechanisms, originating Work, prepared artifacts, outward actions, and evidence path.
The founder does not reconstruct known truth in a blank release form. Missing links remain visible.

## Releases

The Releases rail groups only meaningful release states:

- Needs you;
- Preparing;
- In market;
- Recent.

A selected release presents one causal path:

```text
What changed
      ↓
Who it matters to
      ↓
How value reaches them
      ↓
Exact prepared actions
      ↓
What Drover will observe
      ↓
What returned
      ↓
What changes next
```

The primary action follows the blocking link: clarify the Product consequence, choose an audience, prepare
distribution, review exact actions, release selected actions, review evidence, or begin the next work. There
is no generic Save release action when a specific consequence is available.

## Founder-held consequence

Opening a release or review grants no authority. Exact actions name account, destination, content, tracking,
reversibility, and what will not happen. Apply, send, deploy, spend, publish, destructive actions, and ending
work remain founder-only. Deploy retains separate authorize and execute acts.

## Bounded observation

Observation belongs to the exact release rather than ambient company simulation. A founder-granted contract
names source, purpose, window, and return conditions such as reply, objection, meeting, activation, measured
event, or window close. It is read-only and release-scoped. It authorizes no send, spend, unrelated inward
work, or canonical interpretation change.

## Returned evidence

Returned evidence preserves the exact reply or measured event, source, release join, attribution strength,
and uncertainty. Drover keeps separate:

- what happened;
- what it may mean;
- which Product or go-to-market understanding it affects;
- what work may follow.

A model interpretation stays provisional. The founder may adopt it, challenge it, start Work from it, update
the release, or leave it unresolved.

The explored signature visual is a restrained return curve from evidence to the affected capability,
audience, positioning, offer, or distribution method. The curve expresses a real canonical relationship; it
never manufactures causality.

## Failure and recovery

Every failure state answers what happened, what did not happen, what state was preserved, and the next safe
action.

| Failure | Founder experience | Recovery |
| --- | --- | --- |
| Provider fails | Run stopped before verified work | Resume, branch, or inspect retained worktree |
| Process restarts | Run interrupted; workspace intact | Continue from checkpoint |
| Checks fail | Exact command and affected work | Correct in the same Thread |
| Apply conflicts | No false apply | Rebase, revise, or retain staged work |
| Send fails | Nothing was sent; exact transport error | Reconnect or retry |
| Deploy fails | No deploy occurred; exact receipt | Correct provider or hold |
| Observation fails | Release cannot currently be observed | Reconnect source or let window end honestly |
| Evidence cannot join | Evidence remains unattributed | Attach it or leave it unjoined |
| Interpretation is uncertain | Evidence remains without promotion | Founder decides or leaves unresolved |

## Search and navigation exploration

The original proposal explored a venture-wide command search opening Threads, files, Product / GTM objects,
releases, evidence, decisions, and artifacts in their owning mode. Authority defers that mechanism because it
would introduce a cross-mode result router before direct-reference handoff and the real loop are proven.
Mode-local search remains valid.

## Source-of-truth architecture

Every surface is a projection:

| Truth | Authority |
| --- | --- |
| Code and files | repository/worktree |
| Founder continuity | Drover Thread |
| Execution attempt | Drover Run |
| Provider session | runtime machinery attached to a Run |
| Product/GTM | canonical venture model |
| Release | canonical release references |
| External action | founder decision and effect receipt |
| Returned reality | Evidence/outcome record |
| UI layout | local presentation state |

The Agent SDK boundary emits normalized execution events such as Run started, progress changed, artifact
ready, verification changed, gate required, completed, or failed. It never owns venture structure, Product /
GTM, releases, evidence, workflow identity, or canonical conversation history.

## Experience laws explored

- One venture, three parallel lenses.
- One focal subject carried through direct references.
- One dominant next action where a concrete gap blocks the loop.
- Infer reversible low-cost preparation before interrupting the founder.
- Material dominates when material matters.
- Runtime machinery appears through selected depth.
- No blank forms when truth already exists.
- No fake completion.
- Evidence that changes no understanding stays visibly unresolved.

## Original build sequence

The proposal explored native Work, Work-to-Product/GTM projection, a spatial canvas, generated releases,
observation and evidence return, and compounding methods. The adopted sequence changes the order: prove the
real outward-and-return loop before committing to the broader canvas composition or promotion machinery.

```text
WORK
Founder and agents change the venture
        ↓

PRODUCT / GTM
The consequence and market gap become legible
        ↓

RELEASES
Exact value crosses a founder-held world boundary
        ↓

EVIDENCE
Reality returns with attribution and uncertainty
        ↓

PRODUCT / GTM
Understanding changes provisionally
        ↓

WORK
The next credible change begins
```

The destination remains: select what should become true, develop the necessary Product and market system,
release exact consequences, and let returned evidence visibly reshape the venture without reconstructing
context.
